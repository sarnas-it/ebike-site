# Комментарий к задаче TESTEB-63

<!-- testeb-63-recovery -->

Причина `no_checks` по PR [#62](https://github.com/sarnas-it/ebike-site/pull/62):
застрявший коммит `578e87b5a8587d6078aade92d26bd449448dd1d3` не содержит
`.github/workflows` в своём дереве, а базовая ветка `main` на момент открытия и
последнего push PR была пустой (`40134b5`, `chore: empty repository`) и тоже не
содержала workflow. Для `pull_request` GitHub ищет workflow-файл в дереве PR;
запускать было нечего, поэтому не появилось ни одного прогона — отсюда
`no checks reported for the pull request`. GitHub не запускает workflow
ретроспективно, поэтому появление файла в другой ветке или позже в `main` само
по себе не создаёт прогон для неизменённого старого head.

Это не противоречит тому, что workflow `ci` активен и соседние PR зелёные:
ветки соседних задач (`feat/ebike-site-testeb-15`, `...-44`, `...-50`) сами
добавляют `.github/workflows/ci.yml` в своё дерево, поэтому в их PR workflow
есть. Ветка PR #62 такой файл не добавляла, а `main` тогда был пустым. Actions
включены, фильтров по путям нет, очередь раннеров и лимиты минут не при чём,
allow-list интеграции содержит `sarnas-it/ebike-site`.

Исправление: PR [#65](https://github.com/sarnas-it/ebike-site/pull/65) добавляет
`.github/workflows/ci.yml`, поэтому новые PR получают реальные прогоны на
каждом `pull_request`, `push` в `main` и по `workflow_dispatch`.

Критерий «CI на актуальном head PR #65 успешен» подтверждается штатным прогоном
`ci` на реальном head-коммите PR #65, а не ссылкой на прогон прошлой сдачи.
Workflow `verify-ci-rollout` теперь запускается на самом PR #65
(`pull_request`) и на каждый `push` в `main`; гейт
`scripts/ci/verify-rollout.mjs` сверяет SHA прогона с текущим head и возвращает
код 1, пока:

* PR #65 не нацелен в `main` или не готов к автомержу (конфликты,
  `mergeable=false`, закрыт без мержа);
* `ci.yml` отсутствует в дереве head PR #65 (до мержа) или в `main` (после);
* последний прогон `ci` на **текущем head** (а после мержа — на merge commit)
  не завершился успешно;
* в прогоне нет полного набора job (`php-lint`, `php-tests`, `plugin-tests`,
  `ci-repair-tests`) или какой-то job упал;
* на head нет штатных check runs этих job, привязанных к check suite
  проверяемого прогона `ci` (зелёные check runs, созданные через Checks API в
  обход workflow, не принимаются);
* прогон относится к другому коммиту (например, к предыдущей сдаче).

Мерж PR #65 до ACCEPT не требуется: его выполняет очередь трекера после
приёмки, поэтому до мержа доказательством служит зелёный `ci` и
`verify-ci-rollout` на актуальном head. После мержа тот же гейт переключается
на merge commit и требует зелёный `ci` и штатные check runs уже на нём. Прогон
на другом SHA не принимается, потому что его `head_sha` не совпадает с
проверяемым коммитом; SHA не захардкожен и берётся из PR #65 на момент
проверки.

После зелёного гейта workflow публикует на PR #65 идемпотентный комментарий
`<!-- testeb-63-rollout -->` со ссылкой на штатный run `ci`, его `head_sha`,
списком job, штатными check runs, состоянием `mergeable`/конфликтов и merge
commit (после мержа). Комментарий не создаётся, пока доказательства красные,
поэтому доказательство всегда относится к тому коммиту, который реально
проверялся, а не к прошлой сдаче.

Recovery-workflow `Recover PR #62 checks`
(`.github/workflows/recover-pr62.yml`) выкачивает ровно коммит
`578e87b5a8587d6078aade92d26bd449448dd1d3` (`git rev-parse HEAD` сверяется с
целевым SHA), прогоняет на нём те же проверки, что и обычный CI
(`php-lint`, `php-tests`, `plugin-tests`), публикует результаты на этот SHA и
завершает отложенный мерж PR #62. Мерж выполняется только если все проверки
зелёные и head PR всё ещё равен проверенному коммиту.

Ниже автоматически добавлено подтверждение из реального recovery-прогона:
ссылка на run, результаты проверок на целевом коммите и merge commit. Если
recovery-прогон не завершился успешно или проверки не зелёные, скрипт
`scripts/ci/publish-evidence.mjs` не публикует подтверждение, а завершает job
ошибкой.
