# CI

## Причина `no_checks` по PR #62 (TESTEB-63)

Коммит `578e87b5a8587d6078aade92d26bd449448dd1d3` (head ветки
`feat/ebike-site-testeb-1`) не содержит каталога `.github/workflows` вообще,
поэтому событие `pull_request` не могло создать ни одного прогона. GitHub API
для этого SHA возвращает:

* `GET /repos/sarnas-it/ebike-site/commits/578e87b.../check-runs` —
  `total_count: 0`;
* `GET /repos/sarnas-it/ebike-site/commits/578e87b.../status` —
  `total_count: 0`, состояние `pending`.

Запускать было нечего — это и есть причина состояния
`no checks reported for the pull request`.

Остальные возможные причины исключены:

* GitHub Actions в репозитории включены: workflow `ci` имеет состояние
  `active`, а соседние PR (#59 и #63) в это же время получают успешные
  прогоны;
* фильтров по путям и веткам, из-за которых PR мог бы быть пропущен, в CI нет:
  триггер `pull_request` широкий;
* очередь раннеров и лимит минут не при чём: job на `ubuntu-latest`
  завершается за секунды, как видно по успешным прогонам соседних PR;
* allow-list интеграции содержит `sarnas-it/ebike-site`: PR #62 создан через
  интеграцию, и её токен открывает PR в этом репозитории.

## Что исправлено

В ветку возвращён штатный workflow `.github/workflows/ci.yml` (тот же, что
использовался в `main` и в успешных PR #59/#63):

* запускается на каждом `pull_request` без фильтров по веткам и путям;
* запускается на `push` в `main`;
* выполняет `php -l` для всех PHP-файлов репозитория.

GitHub не запускает новый workflow задним числом для коммита, в дереве
которого этого workflow не было. Поэтому после пуша исправления PR #62
получает новый head, для которого `pull_request` запускает `ci`, а отложенный
мерж выполняется по успешным проверкам нового head без ручного вмешательства.

## Локальная проверка

```bash
find . -name '*.php' -not -path './.git/*' -print0 | xargs -0 -n1 php -l
```

## Комментарий к задаче TESTEB-63

Причина `no_checks`: в коммите `578e87b5a8587d6078aade92d26bd449448dd1d3`
отсутствует `.github/workflows`, поэтому GitHub не создал ни одного прогона
(API: `check-runs total_count: 0`, `status total_count: 0`). Actions включены,
другие PR получают успешные прогоны; фильтров по путям нет, раннеры и лимиты
не при чём, allow-list интеграции содержит репозиторий. Исправление: возвращён
штатный workflow `ci` с проверкой `php -l` на `pull_request` и `push` в `main`.
После пуша новый head PR #62 проходит проверки, и отложенный мерж выполняется
автоматически.
